# ODD Feature: F14 Module 7 — Branch-to-branch transfers

## Objective
Implement the 5 pending features of Module 7 (request, dispatch, reception with verification, differences/damage, plan-gated approval) as a real, usable feature — not a scaffold like F13. New sidebar entry, since this is end-user functionality with its own screens.

## Problem / why
`ESTADO_FUNCIONALIDADES.md` module 7 is 0/5. Unlike module 6, nothing here is externally blocked — D15 is the only related decision and it is "Abierta, Producto/Regencia" (an internal product-rules question: approval rules, partial reception, differences), not an external dependency. Following the module-5 precedent (`f12-pos-module5.md`, D43-D49: reasonable provisional decisions, documented, reviewed with the teacher afterward — no blocking question needed for each one), this feature makes the same kind of provisional calls instead of stalling.

Confirmed during exploration: the SaaS feature flags `transfers` (PROFESIONAL + PREMIUM) and `transfers.approval` (PREMIUM only) already exist in `apps/api/drizzle/0015_core_saas.sql` (lines 140-141, 183-184, 188-189) — someone already intended an approval step gated specifically to the Premium plan. No `transfers`/`transfer_items` tables exist yet. No transfer-related permission exists in `role-templates.ts`.

## Scope
- **Domain model** (new migration after `0026_fiscal_invoices.sql`): `transfers` (tenant/branch-scoped like `purchaseOrders`; `origin_warehouse_id`, `destination_warehouse_id`, `status`, `requested_by`, timestamps) and `transfer_items` (`presentation_id`, `batch_id`, `requested_qty`, `dispatched_qty`, `received_qty`, `difference_reason`). Status machine: `REQUESTED → (APPROVED, Premium only) → DISPATCHED → PARTIALLY_RECEIVED → RECEIVED` plus `CANCELLED`/`REJECTED`.
- **Stock movement timing**: stock leaves the origin's `inventoryBalances.quantityBase` at DISPATCH (not at request) and enters the destination's `quantityBase` at RECEPTION, per the quantity actually received (not dispatched) — avoids phantom stock while in transit. Ledger entries reuse `inventoryMovements` with new `movementType` values `TRANSFER_OUT`/`TRANSFER_IN` (the column is a free 24-char string, no enum migration needed) and `referenceType = 'transfer'` / `referenceId = transfers.id`.
- **Reception with verification + differences**: partial reception allowed (can receive less than dispatched per item, multiple reception events until the transfer is closed); mismatches are recorded as `difference_reason` text per item — no automatic waste/quarantine side effect (that stays a manual, separate action via the existing module-3 flow).
- **Approval flow (Premium only)**: tenants with the `transfers.approval` feature need a `REQUESTED → APPROVED` step (new endpoint, new permission `transfers.approve`) before dispatch is allowed; tenants without it (Profesional plan) go straight from `REQUESTED` to dispatch.
- **New permissions**: `transfers.manage` (request/dispatch/receive) seeded to `owner` (automatic), `regente`, `encargado`, `almacenero`; `transfers.approve` seeded to `owner`, `regente`, `encargado` only (not `almacenero`, not `cajero`).
- **Backend**: `apps/api/src/transfers/` (`transfers.module.ts`, `transfers.controller.ts` gated `@RequireFeature("transfers")`, `transfers.service.ts`), reusing `IdempotencyService`/`AuditService`/`OutboxService` the same way `sales.service.ts` does (`new X(database)`, no extra Nest wiring needed in `sales.module.ts`-equivalent).
- **Frontend**: `apps/web/app/transfers/` — `page.tsx` (list + create request), `[transferId]/page.tsx` (detail: dispatch/receive/approve actions, each conditional on status + permission + plan feature), a `transfers-nav.tsx` only if more than one list-level screen ends up needed (otherwise skip it — don't build sub-nav for a single screen). **New sidebar entry** in `apps/web/app/lib/modules.ts` (`moduleSections`, likely under "Operación"), and add `/transfers` to `tenantRoutes` in `app-shell.tsx`.

## Out of scope
- Anything already covered by other modules: FEFO lot selection reuses the same lookup/lock helpers `sales-fefo.ts` already has, not reinvented here.
- Multi-leg transfers (A→B→C) — a transfer is always one origin, one destination.
- Automatic waste/quarantine from a registered difference — stays a manual follow-up action.

  - Design decisions beyond D53-D56, taken for T2 (documented here for whoever does T3/T4):
    - **Reject is allowed from both `REQUESTED` and `APPROVED`**, not just `REQUESTED`. Rationale: dispatch, not approval, is the actual point of no return (it's the step that moves real stock). An approver who changes their mind — e.g. the origin branch now needs that stock for something else — should be able to reject an already-approved-but-not-yet-dispatched transfer instead of being stuck. Once `DISPATCHED`, rejection is no longer offered (there's nothing left to "reject": the transfer must run its course through reception, or a future out-of-scope cancellation flow).
    - **Approving on a plan without `transfers.approval` is a hard error (`BadRequestException`), not a silent no-op or a tolerated idempotent success.** A Profesional tenant's transfers never need approval (D53); calling `/approve` there would either have to be a confusing no-op or a misleading "success" that implies a gate existed. An explicit, clearly-worded rejection (matching `/Premium/`) is more honest and makes the frontend's job easier (T3 should simply not render the Approve button when the plan feature is off, using the same `transfers.approval` feature flag it will already need to read for other UI decisions).
    - **`rejection_reason` is mandatory** (unlike `transfer_items.difference_reason`, which is optional free text). A rejection without a stated reason leaves the requester with no actionable feedback; a reception difference is just informational bookkeeping. Same 255-char cap and `text()` validator as every other bounded string field in this service, for consistency.
